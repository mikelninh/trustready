# TrustReady dogfood baseline — 2026-08-31

This is the first live public-repository dogfood run of the TrustReady scanner against our own products.

## Read this before the scores

These are **public-repository evidence scores under `core-ai-procurement@2026.08`**, not product-quality, security, legal-compliance, certification or government-readiness scores.

A score of 10 means 2 of the 20 configured controls had evidence strong enough to satisfy the profile from the selected public repository source. A control shown as `candidate` or `not_observed` may exist in reality but remains **unproven by this scan**.

Static repository evidence intentionally cannot verify E3 runtime/deployment controls or E4 organisational/legal attestations.

## What the scanner correctly refused to trust

Across the portfolio, source/document language about the following did **not** automatically become verified runtime evidence:

- human approval / authority boundaries;
- tenant isolation and deployed access control;
- retention and deletion behaviour;
- production audit traces;
- monitoring/regression detection;
- backup/restore/rollback;
- incident-response exercises;
- deployed user-facing AI disclosure.

Likewise, repository documents cannot self-authorise E4 organisational/legal conclusions such as:

- AI provider/deployer role and risk classification;
- named accountable control ownership.

That is intentional. A scanner that upgraded these claims from README text would be easier to impress and much less trustworthy.

## Most valuable common gaps to close

### 1. Automatable / documentable E1–E2 proof

Create dedicated, current, machine-readable evidence where true:

- `MODEL_VENDOR_INVENTORY.md` / structured inventory;
- `DATA_FLOW.md`;
- `SUBPROCESSORS.md`;
- buyer-facing `TRUST_CENTER.md` / assurance pack;
- evidence manifest with `observed_at`, `valid_until` and hashes;
- security vulnerability intake where applicable;
- dependency provenance / lock evidence.

Generating a document is **not enough**. The scanner re-runs its deterministic promotion rule; only the evidence actually satisfying the rule gets promoted.

### 2. E3 runtime proof

Add environment-bound collectors/tests for controls that cannot be proven from Git:

- human approval bypass test;
- explicit AI disclosure observation in the deployed journey;
- cross-tenant isolation probe;
- deletion/retention verification;
- production audit event and replay proof;
- monitoring/alert observation;
- restore/rollback drill evidence;
- incident-response exercise evidence.

Each record must preserve the exact environment, observation time, evidence hash, validity period, collector version and rule version.

### 3. E4 authenticated attestations

Build an authenticated attestation flow for claims only an accountable human can make, including role/risk classification and control ownership.

An unauthenticated Markdown file must never satisfy these controls.

## What happens next

The next sprint is the scan → remediation → re-scan loop:

1. scan;
2. rank gaps by buyer impact and evidence effort;
3. generate/fix only safe E1/E2 artifacts automatically;
4. create runtime proof tasks for E3 gaps;
5. create named attestation tasks for E4 gaps;
6. re-scan with the exact same versioned profile;
7. publish before/after evidence without hiding unresolved controls.

The goal is not to make every score look high. The goal is to make every high score **deserved and independently inspectable**.
